# proj6 设计方案（初稿）

> 队伍：吉人自有天相（国防科技大学）｜赛题：xv6 网络和动态链接功能的设计与实现
> 本文件按平台十章大纲组织；标注「待补」的章节在录制演示与补测后填写。

## 1. 目标描述

在 2026 北航扩展版 xv6（VFS + HAL，支持 xv6fs/ext2/fat32 与 RISC-V/LoongArch）之上：

1. 补齐网络能力：驱动、ARP/IPv4/ICMP/UDP/TCP、socket 系统调用，可运行自带的 ping/udp/tcp 自测；
2. 补齐动态链接：`mmap`、`exec` 的 `PT_INTERP` 与 auxv、用户态 `ld.so`，可运行带 `.so` 依赖的可执行文件；
3. 约束：代码尽量少、运行稳定、双平台可构建、三种文件系统可用，交付相对基线的 diff。

## 2. 题目分析与调研

- 基线结构：`vfs.c` 分发三种文件系统，`block.c` 抽象块设备，`arch/loongarch` 承载平台差异，`hal.c` 收敛中断与启动。
- 关键结论：**新增能力必须挂在既有抽象旁**，而不是改造既有路径——这决定了网络采用 `netdev` 抽象（对齐 `block`），链接采用 `mmap` + 用户态加载器（复用 VFS 读文件）。
- 参考：virtio 1.1 规范（设备初始化与 virtqueue）、RISC-V ELF psABI（重定位类型）、xv6-riscv-book（页表与陷入）。

## 3. 系统框架设计

```
用户程序   ping/udptest/tcptest   dltest/dynhello
────────────────────────────────────────────────
系统调用   socket bind sendto recvfrom connect listen accept
           mmap
────────────────────────────────────────────────
socket 层  struct sock（UDP 队列 / TCP 控制块），复用 struct file 的 FD_SOCK
────────────────────────────────────────────────
协议栈     ARP / IPv4 / ICMP / UDP / TCP（与架构无关）
────────────────────────────────────────────────
netdev     transmit 回调（对齐 block_read_bytes 的厚度）
────────────────────────────────────────────────
驱动       virtio-net：RISC-V = mmio，LoongArch = pci
────────────────────────────────────────────────
链接       exec(PT_INTERP) → ld.so → DT_NEEDED 库 → 重定位 → AT_ENTRY
```

设计取舍：

- **netdev 对齐 blockdev**：协议栈零架构代码；平台差异只在传输层。
- **环回走队列**：目的地址是本机时不递归调用 `ip_input`，避免持有 tcb 锁时重入。
- **解释器映射在 `sz` 之外**：避免从 0 到 0x30000000 的空洞被逐页分配；`proc` 记 `interp_base/size`，退出时先解映射。
- **TCP 先停等**：先保证正确，滑动窗口后补（当前实现一次一段、等 ACK）。

### 6.4 延迟数据

- 外网 ping（QEMU user-mode，到网关 10.0.2.2）：`rtt` 实测在 4500–9000 个 10 MHz 时基计数之间，约 **0.45–0.9 ms**。
- **UDP 环回往返：144 µs/次**（200 次往返共 28987 µs，`rdtime()` 读数，10 MHz 时基）。环回包在系统调用边界投递（`sys_sendto`/`sys_recvfrom`/`sock_read`/`sock_write`），不是等时钟中断。
- **TCP 大块传输：暂缺。** 之前的 panic 根因已定位并修复：`net_loopback_poll` 有 1600 字节局部缓冲，且会被时钟中断调用，嵌套时压爆 8KB 内核栈（`sepc` 落在 `kernelvec` 可证）；改成静态缓冲 + 串行锁后不再 panic。
- TCP 压测程序 `netbench` 的握手阶段已确认正常（加内核打印验证 `ESTAB` 达成）。8KB 环回传输实测 **3465 µs，约 2.3 MB/s**。
- 这个数字是优化后的结果：最初只有 5 KB/s，原因是 `tcp_send` 在内部等 ACK，而环回投递只挂在 `sock_write` 返回之后，等 ACK 期间没人投递，只能等时钟中断（约 100 ms 一次）。在 `tcp_send` 的等待循环里放开锁、投递一次环回、再重新检查（`tcp_wait_ack`），吞吐提升约 470 倍。

## 7. 主要问题与解决（待补，已有素材）

已有素材：ECAM 未映射、`-bios none` 下 BAR 未分配、UDP 伪首部长度、环回重入死锁、`mmap` 缺 `PTE_X`、PA/VA 恒等映射、`freewalk: leaf`、`PHDR not covered by LOAD`、SONAME 缺失、LoongArch BAR 与磁盘 MMIO 重叠、used 环读取缺 `volatile`、virtio-pci 的 virtio-net 头长度为 12 字节。

### 7.1 LoongArch 网卡这一段值得单独写

1. **BAR 与磁盘重叠**：新驱动的 PCI 分配器从 `PCI_MMIO_BASE` 重新开始，和块设备分到同一段地址，导致磁盘寄存器访问失效、`common_cfg` 读成 0，最终 `kerneltrap badv=0`。改成从 +1MB 起分配后消失。
2. **used 环必须 volatile 读**：忙等 `txq.used->idx` 时编译器把读取提到循环外，设备明明写了 used 环，驱动却永远看不到，表现为"TX 超时"。加 `volatile` 后立即正常。
3. **virtio-net 头长度随传输层不同**：virtio-mmio（RISC-V）上是 10 字节，virtio-pci（LoongArch）上按 12 字节解析。按 10 字节填，整帧错位两字节，ARP 请求能发出去但 slirp 直接丢，表现为"TX 成功、收不到任何回复"。
